# 棱版 SVG 接收指引

这份指引回答一个具体问题：**收到一份棱版 SVG，用什么看，看到的结果能不能放行这份稿。**
所有结论都来自 `acceptance/` 下的真实源稿、服务真实输出、查看环境与观测记录；每个数字都能用
`acceptance/harness/run.sh` 重跑。没有实测过的环境在最后一节单列，不并入结论。

先给最短的答案：

| 稿的类型 | 能否用 SVG 放行 | 怎么放行 |
|---|---|---|
| 只有实色填充与仿射变换 | **能** | 实测的浏览器与 SVG 库，1:1 查看（imagemagick 除外，见 §7） |
| 含不透明线性渐变 | **能，限 Chromium / Firefox** | 1:1，整份 SVG 作为文件打开或 `<img>` 嵌入 |
| 含透明渐变（色标 alpha 变化） | **只要颜色，限 Firefox** | 用白/黑两次显示反解颜色与 alpha，见 §4.4 |
| multiply 叠色 | **能** | 结构可判；颜色在整个色域内固有差 ≤8，可判 |
| screen 叠色 | **结构能，颜色不能** | 结构在 SVG 判读；叠色后的绝对颜色以 PNG 为准 |
| 组不透明度 + 半透明形状叠加 | **结构能，颜色不能** | 同上 |
| 二值镂空（evenodd / 裁域 / 蒙版） | **能** | 孔洞看内部，边缘像素差异按 §4.5 判读，不得直接判错 |
| 透明文档底 + multiply/screen | **能，但必须选对嵌入方式** | 见 §3，Chromium 内联与 resvg `--background` 会串底 |

一句话的风险总结：**这个格式能表达棱版的线性光色标插值，但表达不了棱版的线性光图层混合。**
所以"两种看法在原背景上一样、换底后有色差"在 screen 与半透明叠色稿上是**格式的固有差**，
不是谁渲染错了；而"边缘像素不同"多数是覆盖采样差异，也不是组混合算错。
下面用可复现的稿把这几个问题拆开，并且区分"格式本身不允许"与"这个查看器做错了"——
前者换查看器也没用，后者换查看器可以解决。

## 1. 先确认比较基准本身可信

拿服务输出的 PNG 当"标准答案"之前，必须先确认它自己是对的，否则整份对比只是在拿自己的
输出证明自己。

`acceptance/harness/reference.py` 用契约里写明的公式**独立重写**了一遍合成（线性光、
预乘、2×2 覆盖采样、组先压平再按组不透明度混合、二值裁域/蒙版），完全不调用服务代码，
再和真实 PNG 逐探针比较：

| 模型 | 与真实 PNG 的最大差 |
|---|---:|
| 线性光合成（棱版记录的模型） | **1 / 255** |
| 同样结构但直接对 sRGB 值合成 | **61 / 255** |

第一行说明 PNG 可以作为基准（差值只有 8 位舍入）。第二行是整份指引的关键：
**把同一份稿的合成换成 sRGB 画布空间的算法，结果会和棱版差 61。** 后面你会看到，
在**叠色稿**上所有浏览器和多数 SVG 库正好落在这第二行上——它们没有算错，它们在执行
SVG 的合成空间。渐变稿是例外：Chromium / Firefox 会按线性光插值，反而更接近棱版。

两个模型后面反复用到，这里先定义清楚（实现都在 `reference.py`，共用一个 `pixel()`）：

- **线性模型**：先把 sRGB 转线性光，再预乘、做 over 与混合。棱版契约就是这个。
- **sRGB 模型**：结构完全相同（同样先压平组、同样二值裁域/蒙版、同样 2×2 采样），
  只是 over 与混合直接在 sRGB 值上算。这是 SVG 画布不带线性处理时的实际行为；
  §4.3 的因果实验会证明，SVG 的 `color-interpolation` 管不到图层混合。

两者只在**涉及颜色运算**的地方分开：实色、纯几何、镂空内部完全一样；混合、半透明叠加、
渐变色标插值才分开。这正好解释了为什么同一份稿有些像素所有查看器都对，有些却全体偏移。
"全体偏移"是这里的判据：如果某个像素所有查看器都差同一个值、并且正好等于两模型之差，
那是格式问题；如果只有部分查看器偏离、且不落在任一模型上，那是该查看器自己的问题。

## 2. 测试稿：每个只回答一个问题

源稿在 `acceptance/scenes/`，由 `scenes.py` 生成；真实输出在 `acceptance/artifacts/`，
由 `capture.py` 经 HTTP 取自真实服务（含摘要、ETag、重复出图一致性）。

| 稿 | 只回答的问题 | 不含什么 |
|---|---|---|
| `a-solid-control` | 实色与仿射变换能否逐像素一致 | 无渐变、无混合、无透明 |
| `b-backdrop-blend` | multiply/screen 是否把文档底色与已合成图层算进去 | 无组不透明度、无镂空 |
| `c-group-isolation` | 组内两个形状是否只混合一次、组不透明度是否整层施加 | 无渐变、无裁域 |
| `d-gradient-opaque` | 渐变色标是否在线性光里插值 | 无混合、无 alpha |
| `e-gradient-alpha` | 渐变颜色与 alpha 是否预乘插值 | 无混合 |
| `f-transparent-backdrop` | 文档底透明时，混合会不会把查看器底色卷进来 | 无渐变、无镂空 |
| `g-knockout-edge` | 镂空孔洞内部是否稳定、边缘差异有多大 | 无混合 |

每张稿的探针坐标与"这个问题在问什么"写在 `acceptance/scenes/probes.json`，
测量的原始像素在 `acceptance/observations/measurements.json`。

## 3. 查看方式：同一个文件有四种看法，结果不同

这不是吹毛求疵。实测发现**同一个 SVG、同一个浏览器，只因为嵌入方式不同，换底后的颜色就不一样。**

| 代号 | 怎么产生 | 谁受影响 |
|---|---|---|
| `own` | 浏览器截图；或栅格库被指定了页面底色 | 页面底色可能进入混合 |
| `img` | `<img src="…svg">`，SVG 自成合成根 | 页面底色**不会**进入混合 |
| `doc` | 直接把 `.svg` 文件当文档打开（双击） | 同上；页面底色由浏览器决定，且只有一个页面 |
| `post` | 让查看器输出透明画布，再自己叠到指定底色上 | 最贴近"先看 alpha 再决定底色" |

实测（`acceptance/observations/measurements.json` 的 `*_page_spread_opaque`）：
在透明文档底的稿上，Chromium 用 `own` 方式时，**Prism 中不透明**的像素会随页面底色最多变化
**204**（`screen-over-transparent` 探针，白底 255,255,255 对黑底 102,51,204）；
改用 `img` 或直接打开文件，漂移为 **0**。Firefox 的 `own` 方式本身就不串底。
resvg 命令行用 `--background` 会把底色参与混合（同样的探针漂移 204），改为输出透明画布后
自行叠底则为 0。

**因此：拿 SVG 做验收，必须写明嵌入方式。"用浏览器看了一下"不够。**

## 4. 分开判读的四个问题

下面四节对应题面里最难判断的四种情况：背景参与混合、组隔离、渐变插值、镂空边缘。
每一节都只给一条可执行的判据，并说明哪类结论可以据此放行、哪类只能转 PNG。

### 4.1 背景有没有参与混合（`b-backdrop-blend`、`f-transparent-backdrop`）

判据：在 Prism 中不透明的像素，改变查看器页面底色时**不应变化**。
观测表 §3.3 给出每个查看器在三种页面底色下的最大漂移。这一步要放在所有颜色判断之前：
如果底色本身进了混合，后面量到的色差就不是"渲染差异"，而是你自己换底换出来的。结论：

- 用 `img`/`doc` 或 `post` 方式，所有实测查看器的漂移都是 **0**，背景参与方式正确。
- Chromium `own`、resvg `--background` 只在 `f-transparent-backdrop` 这张稿上串底（漂移 204），
  **不能用于判断透明文档底下的混合**；在其余几张不透明底稿上它们都不串底。

这解决了题面里"在原背景上看起来一样、换底后有色差"的第一种成因：
先确认你换底的方式没有把底色塞进混合，再谈颜色。

### 4.2 组隔离与组不透明度（`c-group-isolation`）

这张稿里两个**同色、不透明**的形状叠在同一个 0.5 不透明度层内。重叠处的输入与单形状处完全
相同，所以正确隔离时两者必须**逐像素相等**；如果查看器把不透明度按形状各施加一次，重叠处会
变成 75% 而不是 50%。

实测（观测表 §3.1）：六个查看器在重叠/单形状三点上的最大差都是 **0**。
单看这一条会误判 imagemagick：它三点也相等，但相等的原因是它**整个忽略了组不透明度**，
把形状按全不透明画了出来（单形状 230,76,51，与全不透明源色一致）。
所以本稿配了两条检查：不变量相等 **且** 单形状像素确实被组不透明度压暗过。
加上第二条后，imagemagick 被判为语义失败，其余五个通过。

也就是说这条不变量**全部通过**——"边缘像素不同"不是组混合算错，这一点用本稿可以排除。

组内 multiply 的**绝对颜色**仍会随合成空间变化（见 4.3），但组隔离这个**结构**判定是可靠的。
两个细节值得记下：

- "同色不透明形状"这个构造是必要的。若两个形状颜色不同，压平后的重叠处就等于上层形状，
  与单形状区天然相同，不变量会自动成立、失去区分力——本稿的第一版就有这个缺陷，已修正。
- 组内半透明形状叠加（`op-*` 探针）不满足"输入相同"，不能套这条不变量；它归 4.3 的
  颜色规则处理。

### 4.3 混合与线性光：为什么颜色对不上不是渲染错误（`b-`、`c-`）

这是整份指引最重要的发现，用因果实验确认，而不是靠推断。

`acceptance/harness/format_experiment.mjs` 保持 SVG 其余字节不变，只改
`color-interpolation` 属性，在同一浏览器里重渲：

| 场景 | 原样 | 根改 sRGB | 删除该属性 | 只给渐变加 linearRGB | 只给渐变加 sRGB |
|---|---|---|---|---|---|
| 渐变色标中点 | 184,190,0 | 123,132,0 | 123,132,0 | 184,190,0 | 123,132,0 |
| multiply 像素 | 143,112,62 | 143,112,62 | 143,112,62 | 143,112,62 | 143,112,62 |
| screen 像素 | 153,172,204 | 153,172,204 | 153,172,204 | 153,172,204 | 153,172,204 |

（Chromium 140 与 Firefox 141 结果一致，完整数据见 `observations/format_experiment.json`。）

读法：
- 这个属性**能让渐变色标在线性光里插值**（184 对 123，棱版是 190）。
- 它**完全不影响** multiply/screen 的合成像素（三个数字一模一样）。
- 也就是说 SVG 规范里控制"合成色彩空间"的开关，对图层混合**无效**；
  混合总是在画布的 sRGB 空间里做。

于是 §1 那张表就有了因果解释：凡是叠色稿，任何只做 sRGB 画布合成的查看器，与棱版的差
就等于两种模型的**固有差**。这个差**不取决于某一张稿**，可以整段色域算出来
（`acceptance/harness/blend_sweep.py`，遍历全部 256×256 背底/源色对）：

| 运算 | 固有差最大值 | 出现在 | 全色域内 ≤8 的比例 | 能否只看 SVG 判色 |
|---|---:|---|---:|---|
| multiply | **7.4** | 背底 62、源 62（线性 8，sRGB 15） | 100% | **能**（整个色域都在阈值内） |
| screen | **26.7** | 背底 101、源 101（线性 135，sRGB 162） | 41% | **不能**（只有颜色恰好接近时才碰巧通过） |
| 半透明 over（α=25/50/75%） | **73.2** | 背底 0、源 255、α=0.25（线性 137，sRGB 64） | 52% | **不能** |

这是本指引最实用的一条规则：**multiply 的颜色可以从 SVG 判，screen 和半透明叠加不行。**
前者是格式在两套模型间的差本来就小于阈值；后者只是某些颜色碰巧接近，换一批颜色就会失败，
不能当成可依赖的性质。观测表 §1 里每个机制的"固有差"列，就是这条规则在该稿颜色上的具体值。

所以这些机制要这样放行：

- **结构问题**（有没有混合、混合几次、谁叠在谁上面、孔洞位置）——SVG 可以判断。
- **绝对颜色**：
  - multiply 叠色（`b-backdrop-blend` 的 multiply 部分、`c-group-isolation` 的组内 multiply）——
    **SVG 可判**，实测最好 Δ 1–4。依据是色域扫描：整段色域内固有差上限 7.43，不会因为
    换一批颜色突然超阈值。
  - screen 叠色、半透明形状叠加——**只能由 PNG 放行**。原因不是"这次测得差"，而是这两类
    运算的固有差在部分颜色组合上会超过阈值（screen 最坏 26.7、41% 的组合超 8；
    over 最坏 73.2、48% 的组合超 8），SVG 截图对色号早晚会误判。

关于"边缘像素不同也未必意味着组混合算错"：本指引用两条独立证据确认——
组隔离不变量（§4.2）在所有查看器上差 0，而镂空边缘的差异（§4.5）随采样方式变化但孔洞内部
稳定。两者结合说明差异来自覆盖采样，不是混合对象选错。

### 4.4 渐变插值：两种失败要分开（`d-`、`e-`）

- **不透明渐变**（`d-`）：只有 Chromium 与 Firefox 按线性光插值（中点 G≈190，棱版 184–190）；
  librsvg / resvg / cairosvg 都在 sRGB 里插值（G≈123–132，差 61）。
  这一项**能逐像素放行，但只在 Chromium / Firefox**。
- **透明渐变**（`e-`）：色标 alpha 从 1 走到 0。正确做法是预乘插值——直线色**始终是洋红**，
  只有 alpha 下降。多数查看器把颜色和 alpha 各自插值，直线色会走向灰绿。

  验证方法不依赖查看器是否提供 alpha 通道：用**白底和黑底各看一次**，反解出 alpha 与直线色
  （公式写在 `measure.py:recover_straight`）。实测中点：

  | 查看器 | 反解 alpha | 反解直线色 | 洋红保持 |
  |---|---:|---|---|
  | librsvg | 0.49 | 122,128,122 | 否 |
  | resvg | 0.49 | 126,131,126 | 否 |
  | cairosvg | 0.49 | 124,131,124 | 否 |
  | Chromium | 0.49 | 186,188,186 | 否 |
  | **Firefox** | **0.49** | **255,0,255** | **是** |
  | imagemagick | 1.00 | 0,0,0 | —（整段渐变被画成黑，连 alpha 都没读对） |

  除 imagemagick 外五个查看器的 alpha 都对（0.49），但只有 Firefox 的直线色还在洋红上
  （imagemagick 连 alpha 都错，作为反例另列）。
  **所以透明渐变稿的颜色只能用 Firefox 放行**；其他查看器会把颜色和透明度混在一起算，
  看起来"变淡了"，其实是色相已经漂移。

### 4.5 镂空边缘：边缘像素不同 ≠ 组混合算错（`g-`）

`g-knockout-edge` 用三种方式构造同样的镂空环：evenodd 填充、二值裁域、二值蒙版
（取样方环与菱形，让探针行跨过 45° 边）。
孔洞内部与环体的判断与覆盖率无关；只有**边缘一像素**会因采样方式不同而不同。

实测：孔洞内部与环体，所有查看器差 0–1（librsvg 在环体上为 1，其余为 0）。
沿孔洞左缘扫描时，允许 ±1px 平移后最大差 0–11（`mask-inner-left` 0–1，`fill-inner-left` 7–11，
`clip-inner-left` 5–10；`acceptance/observations/measurements.json` 的 `scans` 同时记录了不平移的差值）。
棱版是每像素 2×2 覆盖采样，浏览器与 SVG 库是解析式抗锯齿；**边缘一像素内的差异属于采样
差异**，不能据此断定组混合或蒙版算错。要判断是否真的算错，看孔洞内部与环体，不看边缘。
Imagemagick 在孔洞内部就差 166，那是真的不对，与本条无关。

## 5. 放行规则

按机制给出，不按整张图笼统给。`STRUCT` = 结构问题可判；`COLOUR` = 绝对颜色可判。

| 机制 | STRUCT | COLOUR | 可用查看器与方式 | 证据 |
|---|---|---|---|---|
| 实色填充 / 仿射 | ✅ | ✅ | 全部实测查看器，任意方式 | §1、表 1 |
| 不透明渐变 | ✅ | ✅（限浏览器） | Chromium 140 / Firefox 141 | §4.4、格式实验 |
| 透明渐变 | ✅ | ✅（仅 Firefox） | Firefox 141，白/黑双底 | §4.4 |
| multiply 叠色 | ✅ | ✅ | Chromium/Firefox/librsvg/resvg；整色域固有差 ≤8 | §4.3 色域扫描 |
| screen 叠色 | ✅ | ❌ | 结构：Chromium/Firefox/librsvg/resvg；颜色：PNG | §4.3 色域扫描 |
| 组隔离 / 组不透明度 | ✅ | ❌（半透明叠加） | 结构：全部实测查看器且不变量差 0（imagemagick 例外，见 §4.2） | §4.2 |
| 二值镂空（内部/环体） | ✅ | ✅ | 全部实测查看器 | §4.5 |
| 二值镂空（边缘一像素） | ⚠️ | ❌ | 不得单看边缘判错 | §4.5 |
| 透明底 + 混合 | ✅ | ✅ | 必须 `img`/`doc`/`post`，不可 Chromium 内联或 resvg `--background` | §3 |

说明：`f-transparent-backdrop` 在观测表 §2 里多条显示 `S–`，因为这张稿的探针要么落在
Prism 全透明像素上（换底本来就该变），要么只有一个页面无从比较；它靠 §3 的专项测量判定，
不靠常规语义检查。这不是缺证据，而是这张稿要回答的问题本来就不在那几项检查里。

**交接时的写法建议：**

- 整份稿判定为 **SVG 可放行**：所有机制都是 ✅/✅，且查看方式与查看器在表列范围内。
- 整份稿判定为 **SVG 看结构、PNG 看颜色**：包含 screen 叠色或半透明组叠加。
  （只含 multiply 的稿不在此列——色域扫描显示 multiply 的颜色可以从 SVG 判。）
  交接口径写成"SVG 用于确认几何、层序与混合关系；颜色以同一稿本的 PNG 成品为准"。
- 整份稿判定为 **仅 PNG**：含透明渐变而接收方只有非 Firefox 环境，或接收方环境无法约束
  嵌入方式。

PNG 不是兜底话术：它是唯一能表达棱版线性光合成的载体（§1 已验证它与独立模型差 1/255）。

## 6. 怎么复现

```sh
# 需要 Go 1.24+、node + Playwright、python3 + Pillow + cairosvg、ImageMagick
GO=/path/to/go acceptance/harness/run.sh
```

依次执行：生成源稿 → 经真实 HTTP 取回 PNG/SVG → 双模型校验 PNG → 六种查看器 × 多种查看方式
渲染 → 格式因果实验与色域扫描 → 逐探针测量 → 生成判定表与观测表。产物：

| 文件 | 内容 |
|---|---|
| `acceptance/scenes/` | 源稿与探针定义 |
| `acceptance/artifacts/` | 服务真实返回的 PNG/SVG 字节 + 摘要清单 |
| `acceptance/observations/render/` | 每个查看器 × 每种方式的截图 |
| `acceptance/observations/measurements.json` | 逐探针原始像素与差值 |
| `acceptance/observations/verdicts.json` | 逐机制判定与放行门 |
| `acceptance/observations/tables.md` | 本文件引用的所有表（由脚本生成，与之同步） |
| `acceptance/observations/blend_gap_sweep.json` | multiply/screen/over 的整色域固有差 |
| `acceptance/observations/format_experiment.json` | `color-interpolation` 因果实验原始截图 |
| `acceptance/observations/environment.json` | 实测环境 + 未测环境 |

本指引里的数字如果和 `tables.md` 不一致，以 `tables.md` 为准——它由脚本从原始 JSON 生成，
不是手写的。

## 7. 没有实测的环境

以下都是接收方可能真实使用的查看方式，本次**没有**测到，不能引用上面的结论：

- **Safari / WebKit**：本机 WebKit（Playwright WebKit 2.46）启动检查直接失败，报告缺
  `libGLESv2.so.2` 与 `libx264.so`（见 `acceptance/observations/environment.json`），
  结果未知。WebKit 的混合与渐变实现可能与 Chromium/Firefox 不同，不能外推。
- **Microsoft Edge、移动端浏览器**：未安装。
- **Chrome / Firefox 的 GUI 窗口**：本次只有无头截图，缩放与显示器色彩配置未覆盖。
- **macOS / Windows**：本机为 Linux arm64；系统级颜色管理未测。
- **Adobe Illustrator、Inkscape、Affinity、Okular、Evince**：未安装。
- **非 1:1 缩放、HDR / 广色域、ICC 配置、打印到纸面**：全部未测。

这些环境如果要用 SVG 放行，必须用同一套稿先在目标环境重跑 §4 的判据；不能把本页的
"✅"直接搬过去。特别是 WebKit，它是唯一有可能在混合色彩空间上与前两者不同的主流引擎，
在它上面得到的结论必须单独记录。

另外，`imagemagick` 在本次是**反例对照**，不是候选查看器：它不实现 `mix-blend-mode`，
渐变透明度也读错（孔洞内部差 166、渐变中点整段拉黑）。在观测表里列出它是为了证明
"这套判据能抓出明显做错的查看器"，而不是推荐。

机器可读的清单在 `acceptance/observations/environment.json` 的 `untested` 字段，
随每次 `run.sh` 重新生成。

## 附：判定阈值

阈值一次写定、统一套用，没有为让某个查看器通过而调参：

| 项 | 阈值（0–255 通道差） | 理由 |
|---|---:|---|
| 实色 | 2 | 8 位舍入 |
| 组隔离不变量 | 2 | 输入相同，只允许舍入 |
| 渐变 | 8 | 线性与 sRGB 中点差约 60，留足区分度 |
| 混合 | 8 | multiply 整色域固有差上限 7.43，阈值必须不低于它 |
| 镂空孔洞 / 环体 | 8 | 与覆盖率无关 |
| 镂空边缘扫描 | 16（±1px 选优） | 采样方式差异，非合成错误 |

阈值定义在 `acceptance/harness/evaluate.py` 顶部。

关于为什么混合只设一条 8：这条阈值对 multiply 恰好在可达范围内，对 screen 与半透明 over
则必然判"不可放行"。这不是阈值太严，而是那两种运算的格式固有差本身就超过 8；
放宽到 27 会让 multiply 失去意义，也会让 screen 的坏颜色蒙混过关。
