# 负空间通道保护改稿

设计师改徽记轮廓时，原稿里需要留空的窄通道常被曲线节点拖动挤没；只量两个标记
点的距离或检查导出 PNG 的像素连通，都无法保证弯曲通道的中段没有被封住。本流程在
修订入口之外提供一条**可验证的受保护通道改稿**路径，所有判定都在服务端同一套编译
几何上完成，预览与最终提交引用同一份稿本文档，因此预览看到的通道度量就是提交稿的
度量。

## 通道的可验证表达

通道不在像素上表达，而在**画布坐标的矢量几何**上表达，由设计师在原稿上标记：

- `centerline`：画布坐标折线（≥2 个点），沿负空间通道的中线走向，允许弯曲；
- `min_width`：通道必须保留的最小**画布宽度** w（正数）。

由二者定义可验证的扫掠断言：以中线上每个采样点为圆心、半径 `w/2` 的圆盘，必须全部
落在负空间内（圆盘不被任何填充边界、图层裁域边界或画布裁域侵入）。这等价于“通道沿
整条中线保持宽度 w”，而不是仅在两端标记点处保持距离；弯曲通道在每个弧长采样点都被
检查。

判定几何与渲染、SVG 导出共用 `geom.Flatten` 的固定细分契约（Q 16 段、C 24 段），
变换后的形状轮廓、图层 `clip`/`mask` 轮廓以及画布矩形共同构成通道边界（`wall`）：

1. 每个形状轮廓点先经形状的仿射 `transform` 映到画布坐标，形状在局部变换下被放大、
   压扁都会如实反映在边界距离里；
2. 同层其他轮廓、其他图层的轮廓、图层裁域与二值蒙版轮廓都参与边界集合，因此通道可
   以由“同层其他轮廓与画布裁域共同围成”；
3. 画布矩形四边始终是边界，通道不能靠移出画布来“保持宽度”。

每个中线采样点执行两项检查：

- **占位检查**：用与栅格器相同的 `Path.Contains`/填充规则判断该点是否落在任何可见
  填充内（图层裁域、蒙版先做同样的剔除）。落入填充的点直接得到间隙 0；
- **边界距离**：计算该点到所有边界线段的最短欧氏距离。

采样沿折线按固定弧长步长进行，步长取 `min(min_width/4, 2px)` 且覆盖全部折线顶点与
端点。通道报告返回 `min_clearance`（全部采样点的最小边界距离）、逐通道的最窄点位置
与限制来源（哪条轮廓/裁域/画布边）。

## 明确的支持范围与几何误差

支持范围是显式界定的：

- 通道保护的是**负空间宽度**（无填充区域），不表达颜色、叠色或渐变语义；
- 判定基于编译后的分段线性轮廓。曲线在细分段之间以弦代替，弦相对真实贝塞尔曲线偏在
  曲线内侧，因此到弦的距离不小于到真实曲线的距离。通道断言因此要求
  `min_clearance ≥ min_width/2 + tolerance`，其中 `tolerance` 取 0.05 个画布单位，
  覆盖 512px 画布内固定细分的最大弦弧偏差，使通过的候选对真实曲线仍然成立；
- 扫掠断言以离散采样逼近连续圆盘扫掠，弧长步长不超过 `min_width/4`，再叠加同一
  `tolerance`，保证两段采样之间发生的收口不会被漏检；
- 形状仅支持现有契约内的仿射变换；非仿射变形不在支持范围内。

## 改稿请求与候选求解

一次通道保护改稿请求（`POST /v1/plates/{id}/corridor-proposals`）包含：

- `revision`：作为原稿的已持久化稿本号；
- `moves`：拖动意图列表。每项定位一个形状路径上的曲线节点（按形状 id 与局部坐标
  匹配 M/L/Q/C 的端点），给出 `to`（期望拖到的局部坐标终点）。同一路径位置被多个
  动词共享时，该节点在各动词中一起移动，保持轮廓闭合；
- `channels`：1..4 条受保护通道（中线 + 最小宽度）。

求解以单一标量 `alpha ∈ [0,1]` 参数化整体拖动：`alpha=0` 为原稿，`alpha=1` 为完整
拖动意图，中间候选按比例插值。这样“偏离原拖动意图的范围”有明确含义：响应给出每个
候选的 `alpha`、各节点实际位移长度与期望位移长度之比，以及最大/最小偏离百分比。

求解过程确定性、有界：

1. 先在原稿（alpha=0）上验证通道。原稿自身不满足保护条件时返回 400，且不产生任何
   候选，报告指出限制来源——没有可保留的基线；
2. 在 33 档固定 alpha 网格（含 0 与 1）上逐档编译并跑全部通道断言；
3. 取满足全部通道的最大可行 alpha。若网格最大值小于 1，在最后一个可行档与第一个
   不可行档之间做 12 次二分细化，得到经断言复核确认的可行边界；
4. 返回至多 5 个按 alpha 升序的候选（alpha=0 的原稿候选、边界候选及其间代表档），
   每个候选携带完整通道报告；
5. 若完整意图（alpha=1）可行，候选包含完整意图；若不可行，`feasible=false`，响应
   仍只给出可行候选，并在 `limit` 中给出收口通道、最窄点与限制边界——**不会静默提交
   被挤没的稿子**。

## 预览与提交一致

提案是瞬态对象（不写入快照、重启即失效，与曝光任务同一生命周期语义），创建时：

- 服务端生成候选稿本文档，并立即用正式渲染路径产出 PNG/SVG 预览成品，成品按既有
  规则持久化并带内容摘要；
- 候选响应包含候选文档的稿本摘要与预览成品 id。

接受候选（`POST /v1/plates/{id}/corridor-proposals/{pid}/accept`）时：

1. 重新从仓库读取当前最新稿本，校验 `expected_revision` 仍匹配（陈旧则 409）；
2. 重新编译候选文档并重跑全部通道断言，任何一条不再通过则拒绝（409），不产生稿本；
3. 断言通过后才把候选文档作为新稿本追加；稿本文档就是预览时渲染的同一份文档，
   `SceneHash` 一致，因此再渲染得到的成品摘要与预览摘要逐字节相同。

无法满足保护条件时不存在可接受候选，原稿与历史不变，限制随提案报告返回。
